# 高密度简历项目经历写作指南

本指南说明 contrib-skill 如何把仓库证据转化为适合开发岗位的项目经历。目标不是增加形容词或技术名词，而是让面试官在一条编号中快速看到：遇到了什么问题、为什么选择该方案、关键机制是什么、最终产生了什么可验证结果。

## 1. 信息如何分配

一段完整的项目经历建议由以下部分组成：

| 区域 | 推荐篇幅 | 核心内容 |
| --- | --- | --- |
| 项目简介 | 1—2 句 | 项目性质、使用场景、目标用户、需求背景、系统边界 |
| 个人贡献 | 3—4 条 | 技术主题、问题/约束、个人方案、关键机制、结果/指标 |
| 技术栈 | 1 行 | 仓库能够证明的语言、框架、数据库、中间件与工程工具 |
| 证据审计 | 不写入简历 | commit、变更文件、背景来源、风险等级、待确认项 |

项目简介负责回答“为什么需要这个项目”，编号贡献负责回答“你具体解决了什么工程问题”。不要让简介比贡献正文更长，也不要在简介中重复罗列整套技术栈。

## 2. 编号贡献的三段式

统一使用以下句式：

```text
技术主题：针对【业务问题或工程约束】，通过/采用【本人负责的技术方案 + 关键机制】；
【形成的业务闭环、工程能力或有证据的量化结果】。
```

三段分别承担不同信息：

1. **问题/约束**：说明为什么要做，例如重复查询、状态跨阶段流转、外部回调衔接、权限边界不清或缺少回归保障。
2. **方案/机制**：说明采用什么方案以及方案如何工作，例如状态驱动、缓存前移、幂等校验、异常隔离、自动化回归或事件解耦。
3. **结果/指标**：优先写可观察结果；只有存在可靠报告时，才写成功率、QPS、P95/P99、覆盖率或缺陷变化等数值。

短技术主题用于提高扫描效率，例如“订单状态建模”“支付回调链路”“查询性能优化”“认证与权限边界”。主题应概括方案，不使用“功能开发”“模块优化”这类低信息词。

## 3. 证据分级与可写边界

| 证据等级 | 可写内容 | 不能外推的内容 |
| --- | --- | --- |
| Git/代码结构证据 | 负责模块、技术方案、设计模式、关键机制、业务闭环 | 线上规模、性能提升比例、用户量 |
| 用户明确提供的背景 | 真实上线、公司内部、开源、课程项目等使用场景 | 仓库无法证明的个人职责和技术实现 |
| benchmark/测试/监控报告 | 测试环境、负载配置、成功率、QPS、延迟分位数、覆盖率 | 没有同条件对照时的“提升百分比”；测试结果不能包装成生产能力 |
| 无直接证据 | 正文外的待确认问题和建议采集指标 | 任何确定性数字、强职责或高可用/高并发结论 |

项目性质按用户明确提供的背景写入正文，同时在审计区标记来源。若用户声明高可用、高并发或生产级，但仓库缺少容错、限流、监控、压测、服务治理等证据，正文保留用户提供的场景，审计区必须提示风险，不能据此虚构架构和指标。

## 4. 技术词汇准入规则

技术词汇必须同时满足两个条件：仓库存在证据，并且该词能够解释问题与方案之间的关系。

- `domain` 目录和领域分层信号可以支持 DDD 倾向；仅有 Controller/Service 不能证明 DDD。
- Controller、Service、Model/Entity 等协同证据可以支持 MVC 或分层架构；单个目录不足以证明完整模式。
- Repository、Strategy、Factory、Adapter、Observer 等模式需要文件名、类名、目录、依赖或 commit 语义直接命中。
- Redis、消息队列、异步任务等组件不能单独成为成果；必须说明它们解决了什么访问、解耦、削峰、重试或一致性问题。

错误写法：

> 使用 Spring Boot、Redis、MySQL、DDD、设计模式完成订单模块开发。

改进写法：

> 查询性能优化：针对订单详情重复读取持久化数据的问题，采用 Redis 构建缓存访问路径，并通过缓存优先、持久化回源机制收敛高频查询；减少 MySQL 重复访问，为后续命中率与尾延迟验证建立可观测入口。

## 5. 指标如何写入结果段

指标必须与当前贡献存在直接因果关系，不能把一次无关压测附加到任意技术方案后面。

| 贡献主题 | 优先补充的真实指标 |
| --- | --- |
| 缓存与查询性能 | 缓存命中率、数据库查询次数、QPS、P95/P99、资源消耗 |
| 订单状态流转 | 流转成功率、异常状态数、处理量、状态处理耗时 |
| 支付回调 | 回调成功率、重复回调比例、异常回调数、处理耗时 |
| 安全与权限 | 未授权请求拦截数、误拦截率、安全事件数、审计覆盖范围 |
| 自动化测试 | 用例数、覆盖率、缺陷回归率、发布前拦截缺陷数 |
| 工程化建设 | 初始化/构建耗时、部署成功率、新模块接入耗时 |

没有报告时，结果段只写可观察能力，例如“形成统一状态承载入口”“建立自动化回归入口”“收敛重复数据访问路径”，具体指标放入正文外的补充建议。

有实测报告时，可直接写入测试边界和结果：

> 接口性能基线：针对订单查询接口缺少可复核性能基线的问题，在本地模拟服务的测试环境编写并执行 HTTP 压测脚本，以 10 并发完成 100 次请求；实测成功率 100.00%、吞吐量 184.30 QPS、P95 延迟 11.02 ms，为后续容量评估与性能优化建立量化基线。

上述数值来自仓库保存的本地模拟报告，仅用于展示格式。只有存在同环境、同配置的改造前后报告时，才能进一步表述“提升多少”；测试环境结果不能写成生产承载能力。完整数据来源见[本地压测数据示例](benchmark-resume-example.md)。

## 6. 生成后检查清单

- 项目简介是否先交代需求背景，再说明系统边界和整体方案？
- 每条编号是否都能找到明确的问题、方案/机制和结果？
- 技术名词是否有目录、文件、依赖或 commit 证据？
- “主导、独立负责、从 0 到 1”是否符合作者贡献和模块归属？
- 每个数值是否能回溯到 benchmark、监控、测试报告或用户提供的可靠来源？
- 本地/测试/预发布数据是否明确写出环境，且没有外推为生产能力？
- commit hash、文件路径、风险等级是否留在审计区而非简历正文？

生成结果可结合[完整输出示例](example-output/06_resume_bullets.md)检查；项目背景声明、贡献归属与指标证据仍以[风险报告示例](example-output/08_claim_risk_report.md)和[结构化证据示例](example-output/evidence.json)为最终审计依据。
